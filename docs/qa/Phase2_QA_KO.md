# ScrollGuard Phase 2: 예상 질문과 답

질문마다 소리 내어 말할 수 있는 한 줄 답을 먼저 쓰고, 그 아래에 근거 수치를 붙였어요. 수치는 모두 저장소(`docs/results/`, `docs/annotation/results/`)와 Phase 2 보고서에서 가져왔어요.

---

## 1. 여기에 들어간 에이전트 기술은?

**한 줄 답.** 이 벤치마크는 에이전트를 평가하는 도구이고, 평가에 쓴 에이전트에는 도구 호출, ReAct 방식의 루프, 에이전트형 검색(agentic retrieval), 근거를 먼저 쓰는 구조화된 출력이 들어 있어요.

| 기술 | 어디에 | 강의 |
|---|---|---|
| 도구 호출 (function calling) | 트랙 B: 터치 기록, 통계, 사용자 맥락 도구 3개를 JSON으로 호출 | Ch11 |
| 에이전트 루프 (ReAct 방식) | 트랙 B: 판단 → 도구 호출 → 결과 관찰 → 다시 판단, 최대 4회 | Ch13 |
| 에이전트형 검색 (agentic RAG) | 목표와 관찰 기록을 처음부터 주지 않고 에이전트가 스스로 찾게 함 | Ch05 |
| 구조화된 출력, 근거 우선 | `{"reason": ..., "action": ...}` 순서, 형식 오류 복구와 재시도 | Ch04 |
| 워크플로 vs 에이전트 | 트랙 A(정보를 다 줌) vs 트랙 B(스스로 찾음) | Ch13 |
| 프롬프트·도구 설계 | 입력 열 설명, 도구 설명, 도구 순서 | Ch04, Ch11 |

---

## 2. 어떻게 평가하나? 입력과 출력, 기대 행동은?

**한 줄 답.** 에이전트가 사용 상황 하나를 읽고 세 행동 중 하나를 고르면, 그 행동을 사람이 검증한 정답과 자동으로 비교해요.

- **입력:** 상황(시각, 앱, 진입 계기), 사용자(선언한 목표, 상태), 5칸 관찰 기록, 사용량·제스처 숫자예요.
- **출력:** JSON 한 줄, `{"reason": "...", "action": "..."}`이에요.
- **기대 행동:** 사례마다 정답 행동이 하나씩 있고, 문서로 정한 라벨링 규칙을 따라요.
  - `no_intervention`: 의도적이거나 정상적인 사용
  - `gentle_prompt`: 자동조종 사용. 독립적인 자동조종 신호가 2개 이상이고 반대 증거가 없을 때
  - `ask_context`: 신호가 충돌하거나 판단에 필요한 정보가 부족할 때
- **채점:** close-ended 방식이에요. 행동만 채점하고, 근거는 오류 분석에만 써요.
- **지표:** 정확도 하나가 아니라 여러 지표를 함께 봐요.
  - 정확도와 95% 신뢰구간
  - 불필요 개입률 (핵심 제품 지표)
  - 탐지율
  - `ask_recall`과 질문 부담
  - 반례 쌍
  - 비용 점수
  - 트랙 B의 맥락 확인율
- **예시 (S013):** 사용자가 "5분만"이라고 적었는데 짧은 영상 520개가 재생됐어요. 기대 행동은 `gentle_prompt`예요.

## 3. 에이전트가 이상한 질문을 하면?

**한 줄 답.** 지금은 "묻겠다"는 결정만 채점하고 질문 문장은 채점하지 않아요. 불필요한 질문은 감점하고, 문장 평가는 다음 단계예요.

- `ask_context`는 결정이에요. 에이전트가 질문 문장을 쓰지 않으므로 문장은 **아직 평가하지 않아요.** 이건 한계예요.
- **이미 잡고 있는 것:**
  - **묻지 않아도 될 때 묻는 경우:** 질문 부담에 들어가고, 비용은 0.8이에요. 불필요한 개입(1.0)에 가까운 무게예요.
  - **세 행동 밖의 답:** 무효로 채점해요(`invalid_rate`).
  - **형식이 깨진 답:** `PARSE_ERROR`예요. 트랙 B는 안내 후 2번까지 다시 물어요.
- **다음 단계:** 에이전트가 질문 문장을 쓰게 하고, 루브릭(관련성, 중립성, 간결함)으로 사람이나 LLM 심판이 채점하는 방법이에요. 강의의 open-ended 평가 방식이에요.

## 4. 데이터셋이 너무 적은 것 같은데?

**한 줄 답.** 맞아요, 81개는 작아요. 그래서 차이가 큰 결과만 결론으로 쓰고 작은 차이는 해석하지 않아요.

- 81개면 정확도 신뢰구간이 약 ±0.1이에요. 0.62 vs 0.63 같은 차이는 해석하지 않아요.
- **작게 만든 이유:** 사례마다 맥락을 직접 썼고, 사람 2명이 전부 라벨링했어요. 수를 늘리기보다, 각자 특정한 실패를 노리는 진단용 사례(대립형, 경계형, 반례 쌍, 지름길)에 집중했어요. 참고로 강의에서 다룬 HumanEval도 164문제예요.
- **결론으로 쓴 차이는 커요.**
  - 도구 순서: 맥락 확인 13% → 100%
  - 오류 방향: 60% vs 15%
  - 묻기: 사람은 15번·9번, 모델은 486번 중 2번
- **보정 장치:** 부트스트랩 95% 신뢰구간, 트랙 A의 사례당 3회 반복, 두 라벨러가 합의한 65개 기준 재채점을 썼어요.
- **확장 방법:** 실제 데이터 5,777행이 있으니 템플릿으로 사례를 늘리고, 사람은 표본만 검증할 수 있어요. 다만 템플릿으로 늘리면 지름길이 다시 생기기 쉬워서, 지름길 검사를 함께 돌려야 해요.

## 5. 정답은 어떻게 만들었나?

**한 줄 답.** 라벨링 규칙을 먼저 정하고 그 규칙으로 정답을 만든 뒤, 독립된 사람 2명이 정답을 보지 않고 81개를 모두 라벨링했어요. 그리고 5개를 다수결로 고쳤어요.

1. 라벨링 규칙을 문서로 정했어요. 예를 들어 `gentle_prompt`는 독립적인 자동조종 신호 2개 이상 + 반대 증거 없음이에요.
2. 그 규칙으로 원래 정답(설계 정답)을 만들었어요(AI 보조 작성).
3. 설계에 참여하지 않은 2명이 정답을 보지 않고 81개를 모두 라벨링했어요.
4. 두 라벨러가 모두 원래 정답과 다르게 고른 5개는 2:1 다수결로 정답을 고쳤어요.

최종 정답: `no_intervention` 34개, `gentle_prompt` 32개, `ask_context` 15개예요.

## 6. 이 정답률을 믿을 수 있나? 사람이 풀어도 성립하나?

**한 줄 답.** 같은 정답으로 사람은 약 0.8, 7B 모델은 약 0.6을 맞혀요. 정답은 믿을 만하고, 격차는 실제 격차예요.

아래 표는 모두 **다수결로 고치기 전의 원래 정답**을 기준으로 했어요. 라벨러가 정답을 바꾸는 데 참여했으니, 고친 정답으로 비교하면 라벨러에게 유리해지기 때문이에요.

| 누가 | 원래 정답과 일치 | Cohen's kappa |
|---|---|---|
| 라벨러 A | **0.84** | 0.75 |
| 라벨러 B | **0.81** | 0.71 |
| 라벨러 A vs B (서로) | 0.80 | 0.68 |
| 세 평가자 전체 | | Fleiss' kappa 0.71 |
| Qwen 트랙 A (1회차) | 0.67 | 각 라벨러와 0.39~0.40 |
| EXAONE 트랙 A (1회차) | 0.59 | 각 라벨러와 0.28~0.29 |
| Qwen 트랙 B | 0.40 | 각 라벨러와 약 0 |

- **어떤 kappa인가:**
  - **Cohen's kappa:** 두 평가자 사이의 값이에요. 라벨러끼리, 또는 라벨러와 원래 정답 사이예요.
  - **Fleiss' kappa:** 셋 이상일 때 써요. 두 라벨러와 원래 정답 셋을 함께 본 값이 0.71이에요.
- **정답을 믿을 수 있어요:** 독립된 두 사람이 원래 정답과 81~84% 일치했어요. kappa 0.71~0.75로 "상당한 일치"예요.
- **과제를 풀 수 있어요:** 사람은 약 0.8을 맞혀요. 그러니 모델의 약 0.6은 불가능한 시험이라서가 아니라 실제 격차예요.
- **사람도 갈리는 곳이 있어요:** 범주에 따라 일치도가 크게 달라요.

  | 원래 정답 | 라벨러 A | 라벨러 B |
  |---|---|---|
  | `no_intervention` | 1.00 | 0.97 |
  | `gentle_prompt` | 0.84 | 0.94 |
  | `ask_context` | 0.56 | 0.33 |

  그래서 합의된 65개 기준 점수를 함께 보고해요. 순위는 같아요: Qwen A 0.71, EXAONE A 0.68, 규칙 B2 0.62.

## 7. 트랙 A와 B를 나눈 이유는?

**한 줄 답.** 두 능력을 따로 재려고요. 주어진 맥락을 해석하는 능력(A)과, 맥락을 스스로 찾는 능력(B)이에요.

- **각 트랙이 재는 것:**
  - 트랙 A는 정보를 한 번에 다 줘요. 판단력, 즉 맥락을 제대로 읽는지를 재요.
  - 트랙 B는 시각, 앱, 사용량만 주고 나머지는 도구로 찾게 해요. 에이전트 능력, 즉 무엇이 필요한지 알고 찾아오는지를 재요.
- **나머지는 똑같아요:** 행동 정의, 출력 형식, 사례가 모두 같아요. 그래서 A에서 B로 떨어진 만큼이 정보 탐색에서 생긴 차이예요.
- **강의와 맞닿아 있어요:**
  - 워크플로 vs 에이전트 (Ch13)
  - 에이전트 벤치마크는 답만이 아니라 궤적을 채점한다 (Ch03)
- **나눈 효과가 있었어요:**
  - 같은 Qwen이 0.63(A)에서 0.42(B)로 떨어졌어요. 맥락을 9%만 확인했기 때문이에요.
  - 트랙 B가 있어서 도구 순서 실험도 할 수 있었어요. 맥락 도구를 목록 맨 앞으로 옮기자 Qwen의 맥락 확인은 13% → 100%로 올랐고, EXAONE은 0~3%에 머물렀어요. 같은 현상의 원인이 서로 달랐는데, 트랙이 하나였다면 볼 수 없었어요.
- **현실적이기도 해요:** 휴대폰에서 사용자 맥락을 읽는 데는 비용(개인정보, 배터리)이 들어서, 실제 에이전트는 언제 정보를 가져올지 스스로 정해야 해요.

## 8. `ask_recall`이 너무 낮은데, 벤치마크에 문제가 있는 거 아닌가?

**한 줄 답.** 아니에요. 같은 사례에서 사람은 실제로 물었으니, 낮은 점수는 평가한 두 에이전트의 실제 약점이에요(둘 다 4비트 7B 모델이라 모델 일반에 대한 주장은 아니에요). 남은 약점은 이 범주의 사례가 적다는 것이고, 그건 한계로 보고하고 있어요.

- **과제는 가능해요:** 같은 입력을 보고 라벨러 A는 "먼저 묻기"를 15번, B는 9번 골랐어요. 두 모델은 트랙 A의 486번 판단에서 2번 물었고, 둘 다 오답이었어요.
- **정답이 애매해서가 아니에요:** 두 라벨러가 모두 동의한 `ask_context` 5개에서도 모델은 0번 물었어요.
- **정의가 모호해서도 아니에요:** 실험 1에서 두 행동의 정의를 더 분명히 나눴어요. 묻기는 0/15 → 2/15로 조금 늘고, 불필요 개입은 0/8 → 3/8로 늘어서 채택하지 않았어요. 모델은 근거에 충돌을 직접 쓰고도("could indicate mindless scrolling. However, ... some intentional use") 한쪽을 골랐어요.
- **정보가 없어서도 아니에요:** 맥락 도구를 맨 앞에 두자 Qwen은 100% 맥락을 읽었지만, 그래도 한 번도 묻지 않았어요.
- **지표를 찍기로 이길 수 없어요:** "항상 묻기" 기준선은 `ask_recall`이 1.0이지만, 불필요한 질문이 감점돼서 정확도 0.19, 비용 점수 0.47로 가장 낮은 축이에요.
- **핵심 목표는 따로 잘 재고 있어요:** 정답이 `no_intervention`이나 `gentle_prompt`인 66개에서 트랙 A 모델은 0.76~0.77, 최고 규칙은 0.65예요.
- **진짜 약점:** 이 범주는 15개뿐이고 두 라벨러가 합의한 건 5개예요. 사람끼리도 가장 많이 갈리는 범주예요. 그래서 모델끼리 묻기 능력을 비교할 통계적 힘이 약해요. 다음 버전에서는 "먼저 묻기" 사례와 라벨러를 늘리고, `ask_recall`을 합의된 사례 기준으로 보고해야 해요.
